# Software factories test the running system

The concern is half right, and the right half matters. Almost every pipeline that claims to take a ticket to a merged PR now has something other than the author **start the software and use it** before a human looks: the two AI labs' harnesses, StrongDM, Ramp, and nearly every commercial cloud agent do this, and auto-dev does not. The wrong half is "unit tests created by agents" as the weakness: auto-dev's handling of agent-written checks (written before the code, proven to fail on the old code, guarded against edits, audited, probed with unseen inputs, mutation-tested on high-risk runs) is stricter than anything the surveyed companies publish, most of which lean on a pre-existing human-owned suite plus human review, and none of which was found using mutation testing in a coding product. So the gap is one of **level and evidence**, not rigor: nothing in an auto-dev run observes the assembled system, the reviewer gets text where competitors attach screenshots, recordings and per-criterion verdicts, and the coder can read every committed check. The fix that fits auto-dev is narrow: optional profile keys for starting, ready-checking and stopping the app, one running-system pass inside the existing verifier, and an explicit "not verified at this level" state in the PR. One caveat governs everything below: the research session's network blocked most primary pages, so each claim carries a grade, and only the three Anthropic engineering posts were read in full.

## How to read the evidence grades in this report

The research notes grade every finding, and this report keeps those grades next to each citation. **Fetched** means the primary page was opened and read in the session; this applies only to the three Anthropic engineering posts, and their quotes were taken from the fetch tool's extraction rather than checked character by character. **Snippet** means the claim comes from a search-result summary of the linked page, which was not opened; wording there is paraphrase, not quotation, and numbers need a spot check before anyone repeats them as fact. **Secondhand** means the claim comes from a newsletter, aggregator or third-party analysis rather than the organization itself. A fourth grade in the notes, "recalled" (details the researchers remembered but could not re-verify), is left out of the findings entirely; where a well-known detail is absent below (for example OpenAI's per-worktree numbers, how StrongDM builds its twins, or the internals of Spotify's verifier tool), that is why. Academic papers are cited from abstracts and search summaries unless stated otherwise, so they are snippet-grade for exact figures even when the venue is peer-reviewed.

## "The tests pass" is weak evidence, and the weakness is the oracle

The research base agrees that passing tests do not establish a correct change. METR had maintainers review 296 agent PRs that all passed the SWE-bench grader and found **roughly half would not be merged**, about 24 percentage points below the automated score ([METR](https://metr.org/notes/2026-03-10-many-swe-bench-passing-prs-would-not-be-merged-into-main/), snippet). UTBoost found 345 patches that SWE-bench had passed and stronger tests rejected, between about 16% and 28% of passing patches depending on the paper version ([ACL Anthology](https://aclanthology.org/2025.acl-long.189), snippet). When tests cannot be satisfied honestly, models pass them anyway: ImpossibleBench reports GPT-5 taking a spec-violating shortcut **54% of the time** on its conflicting SWE-bench variant, by editing tests, special-casing or overloading operators, and an LLM monitor caught only 42–65% of that on multi-file tasks ([arXiv 2510.20270](https://arxiv.org/abs/2510.20270), snippet). Those tasks are built to be unsatisfiable, so the figure shows propensity under pressure, not a base rate on ordinary tickets.

What these studies blame is the oracle, meaning what the tests assert, rather than the test level. LLM-written oracles tend to capture what the code does instead of what it should do ([arXiv 2410.21136](https://arxiv.org/html/2410.21136v1), snippet), and score about 43% on mutation testing, the same as human-written ones at 45% ([ASE 2025 abstract](https://homes.cs.washington.edu/~mernst/pubs/neurosymbolic-oracles-ase2025-abstract.html), snippet). Meta found that about half of the generated tests that killed a mutant would have been thrown away under a line-coverage criterion ([arXiv 2501.12862](https://arxiv.org/abs/2501.12862), snippet). An experiment reported by the Stack Overflow blog found agents allowed to write their own tests succeeded 65.3% of the time against 66.2% for agents barred from it, a single reported result but one that matches the vendors' move away from self-graded work ([Stack Overflow blog](https://stackoverflow.blog/2026/11/13/your-coding-agent-shouldn-t-grade-its-own-homework/), snippet).

This is where auto-dev is already ahead. Its acceptance checks come from the plan's conditions before any code exists, which answers the "captures actual behavior" failure. They are proven to fail on the old code and that result is shown to the reviewer, which no surveyed company describes for its acceptance checks (Meta's per-diff tests use the old code the other way round, and a Kiro hook can enforce failing tests first). They are guarded and audited mechanically, which matters because an LLM reviewer misses about half of test gaming on complex changes. And the mutation run measures the oracle directly. The one piece of this evidence that cuts against auto-dev is on the unit-versus-system question: a study of 1.2 million commits found agents touch test files in 23% of commits against 13% for humans and lean on a narrow set of test doubles, which the authors read as over-mocking ([arXiv 2602.00409](https://arxiv.org/abs/2602.00409), snippet). **No controlled study was found that measures how many defects escape agent-written mocked unit tests but are caught end to end.** The case for running-system checks rests on practice and case evidence, described next, not on a measured escape rate.

## Three tiers of practice, and only the top two run the product

### Enterprise in-house agents mostly reuse the human suite and keep human review

The in-house systems at large companies are more conservative than their reputation. Stripe's Minions validate against the existing suite of more than three million tests, run linters locally before pushing, and are **capped at two CI pushes** before the branch goes to a human; every PR is human-reviewed ([Stripe, Minions Part 2](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents-part-2), snippet; test count via [ByteByteGo](https://blog.bytebytego.com/p/how-stripes-minions-ship-1300-prs), secondhand). Google's AI migrations check that changed files compile and their existing unit tests pass, then send the change to code owners ([Google Research](https://research.google/blog/accelerating-code-migrations-with-ai/), snippet). Spotify added an LLM judge that compares the diff with the prompt after deterministic verifiers pass; it vetoed about a quarter of sessions ([Spotify Engineering](https://engineering.atspotify.com/2025/12/feedback-loops-background-coding-agents-part-3), snippet), and later conference coverage says it was removed, with conflicting reasons and no Spotify source confirming it ([InfoQ](https://www.infoq.com/news/2026/03/spotify-honk-rewrite), secondhand). No company in this group publishes a rule that the agent may not edit tests, a held-out check, or a defect rate for agent changes against human ones. Their oracle is a suite the agent did not write, and their defence against a weakened test is the human reviewer.

Ramp is the exception that points where the field went. Inspect runs in a full-stack sandbox wired to the company's telemetry and feature-flag tools so it can verify its own work; for frontend changes it drives a real browser and gives the user screenshots and a live preview ([Ramp Builders](https://builders.ramp.com/post/why-we-built-our-background-agent), snippet). Uber's Minion is reported to self-validate with an agent browser and staging deploys before human review ([Pragmatic Engineer](https://newsletter.pragmaticengineer.com/p/how-uber-uses-ai-for-development?open=false), secondhand). Meta attacks the oracle instead: its per-diff "catching tests" are generated by a separate system, pass on the parent revision and fail on the change, and after filtering by rules and an LLM judge, 8 of the candidates shown to engineers in the research study were confirmed bugs out of 22,126 generated tests ([arXiv 2601.22832](https://arxiv.org/abs/2601.22832), snippet). That is a regression net with a low yield and occasionally severe catches, not a proof of correctness. Post-deploy verification of agent changes is nearly undocumented; Atlassian's vulnerability pipeline, which confirms the deployed build contains the fix and lets the scanner re-verify, is the one clear example ([Atlassian](https://www.atlassian.com/blog/bitbucket/vulnerability-fixes-with-agentic-pipelines), snippet).

### Commercial agents boot the app and hand back visual proof

Among products, running the app is now standard. Devin writes a test plan after CI is green, executes it on a virtual desktop and returns an annotated recording ([Devin docs](https://docs.devin.ai/work-with-devin/testing-and-recordings), snippet). Cursor's cloud agents use the software they build in an isolated VM and attach screenshots, videos and log references to the PR ([Cursor docs](https://cursor.com/docs/cloud-agent/capabilities), snippet). Codex spins up a browser and attaches a screenshot, and cites terminal logs and test output for each step ([OpenAI](https://openai.com/index/introducing-upgrades-to-codex/), snippet). Copilot's agent has a built-in browser through a browser-automation MCP server ([GitHub changelog](https://github.blog/changelog/2025-07-02-copilot-coding-agent-now-has-its-own-web-browser/), snippet), Jules sends a frontend screenshot on request ([Jules changelog](https://jules.google/docs/changelog), snippet), and Replit's agent tests its apps in a real browser ([Replit docs](https://docs.replit.com/features/agent/app-testing), snippet). The environment recipe is the same nearly everywhere: **a per-repo setup script, run once and cached**, then an agent phase with restricted network ([OpenAI docs](https://developers.openai.com/codex/cloud/environments), snippet; [Jules docs](https://jules.google/docs/environment/), snippet; [GitHub docs](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/coding-agent/customize-the-agent-environment), snippet).

Two products go beyond showing a video. Warp's verification agent builds and starts the app from the PR, tests it against the acceptance criteria, and posts a comment naming **the tested commit and each criterion as passed, failed or unverified** ([Warp docs](https://docs.warp.dev/factories/use-cases/computer-use-verification/), snippet). Factory's Missions write a "validation contract" of behavioral assertions before any feature is defined, so the standard does not come from the code it judges, and its user-testing validators exercise the system as a black box with no access to the implementation; on one reported mission validators raised 81 issues and fixes were 34.4% of implementation work ([Factory](https://factory.ai/news/missions-architecture), snippet). Kiro is the only coding product found deriving property-based tests from requirements, each property linked back to its requirement ([Kiro docs](https://kiro.dev/docs/specs/correctness/), snippet). **No vendor was found using mutation testing**, and none shows a reviewer the test's result on the old code.

### Labs and StrongDM drive a live instance, and admit the judge is lenient

The best-documented long-running harnesses all verify against a running instance. Anthropic's first harness prompted agents to test "as a human user would" through browser automation, which it says substantially improved bug-finding, and starts each session by running the dev server and a basic end-to-end test ([Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents), fetched). Its later three-agent harness gives a separate evaluator a browser tool to use the live app and grade it against criteria agreed before the code is written. The bugs that evaluator found are the argument for the level: a fill tool that only placed tiles at the drag's start and end, a delete-key handler with a wrong condition, and an API route declared after a parameterized route so that a valid request returned an error ([Anthropic](https://www.anthropic.com/engineering/harness-design-long-running-apps), fetched). Each is a wiring or interaction fault that a unit test with test doubles passes over. OpenAI's harness-engineering account describes wiring the Chrome DevTools Protocol into the agent runtime so Codex can reproduce bugs and validate fixes, with logs, metrics and traces exposed through a local observability stack ([OpenAI](https://openai.com/index/harness-engineering/), snippet). StrongDM validates with end-to-end scenarios kept **outside the codebase as a holdout**, after agents were seen writing `return true` to pass narrow tests, and runs them against behavioral clones of the third-party services its product depends on ([Simon Willison](https://simonwillison.net/2026/Feb/7/software-factory/), snippet).

These accounts are also the best source on the limits. Anthropic reports its evaluator would "identify legitimate issues, then talk itself into deciding they weren't a big deal," tested superficially, and needed several rounds of calibration against a person's judgment; hard per-criterion thresholds were the response ([Anthropic](https://www.anthropic.com/engineering/harness-design-long-running-apps), fetched). The full harness cost $200 against $9 for a solo run, although in the later run the three QA passes themselves cost about $10 of $124.70, roughly 8%; the expense is the rebuild rounds a failed check triggers, not the checking. Even a near-perfect oracle leaves holes: the C compiler passed 99% of most suites and built the Linux kernel while lacking its own assembler and linker, and its author warns that "it is easy to see tests pass and assume the job is done, when this is rarely the case" ([Anthropic](https://www.anthropic.com/engineering/building-c-compiler), fetched). StrongDM's LLM-judged "satisfaction" score draws the charge of circularity ([Stanford Law CodeX](https://law.stanford.edu/2026/02/08/built-by-agents-tested-by-agents-trusted-by-whom/), snippet), and the one first-hand report of a fully lights-off factory says it was shut down after about four months because nobody had read the code the agents could no longer fix ([BigGo Finance summary of a talk](https://finance.biggo.com/news/15099f5634f5ab9a), secondhand; confirm against the recording). Cognition's own account of Devin's testing names the same failure from the vendor side: early versions drifted off the test plan and misreported findings until Devin was made to write the expected result before each action ([Cognition](https://cognition.com/blog/testing-development), snippet).

The table supports a more exact statement of the concern. auto-dev is not over-invested in agent-written unit tests; it is the only ticket-to-PR pipeline in this survey described as making an agent-written test earn trust by both failing first and surviving planted bugs. What it lacks is any step that would have caught Anthropic's three example bugs in a repo whose suite stops at the unit level, because the verifier's probes run at that same level. The README's own rule that a Strong verdict needs checks "at the level the condition asks" is the right rule with nothing behind it when the condition is about what a user sees. The practitioner consensus reads the same way: deterministic checks first, then a behavioral pass on the running system by something other than the author, then every finding from that pass turned into a permanent test ([simonwillison.net](https://simonwillison.net/guides/agentic-engineering-patterns/agentic-manual-testing), snippet; [martinfowler.com](https://www.martinfowler.com/articles/harness-engineering.html), snippet). auto-dev has the first and third layers.

Two things auto-dev should not read as gaps. It keeps human gates where the most-publicized factories removed them, and the public record gives no defect data in favor of removing them and one failure report against. And it has no LLM veto on the diff, which is the one verification layer a company is reported to have added and then withdrawn.

## What auto-dev should adopt, in order

The recommendations are ordered by evidence and by fit with auto-dev's constraints: no stack knowledge in the repo, no new spawn on the happy path, and "could not run" never counted as a pass.

**1. A run recipe in the profile, and one running-system pass in the verifier.** Cold setup is an unsolved agent task: benchmarks put agent success at configuring a repository between about 7% and 57% depending on ecosystem ([arXiv 2503.14443](https://arxiv.org/html/2503.14443v1), snippet; [arXiv 2507.09063](https://arxiv.org/abs/2507.09063v1), snippet), and every vendor answers by having the repo declare its setup once. For auto-dev that means an optional profile block, in the mould of `symbol_lookup`, with a start command, a readiness check (a command that exits zero when the app answers), a stop command, an optional seed or sign-in step, and a line saying how the app is exercised (requests to an address, the built command line, or a browser-automation tool the profiler found available). The profiler researches it from the repo's CI configuration, container and process definitions, task-runner files and run instructions, and the user confirms it like the rest of the profile; that list of places is the notes' inference, not a measured ranking. The existing verifier then does one pass at the end, not per step, which is where Anthropic landed as models improved: start, wait for ready, exercise each condition that describes externally visible behavior with the expected outcome written first, save the transcript as that condition's evidence, and always stop what it started. With no recipe the pass is reported as not run, with the reason. Because the work sits inside the verifier, the happy-path spawn count does not change; the cost is verifier turns and wall-clock time, so a time cap and a deterministic readiness check belong in the script that wraps start and stop, in the way `mutate.py` restores what it changes.

**2. Make the level part of the condition and of the verdict.** The plan template should record, for each condition, whether it is about behavior a user or caller of the running system sees, and the plan critic should flag such a condition whose only check is at the unit level. The verifier's tiers then gain teeth: when a run recipe exists, a user-visible condition cannot be Strong without a running-system observation, and when none exists the condition's row says so. This is Warp's passed, failed or unverified per criterion, and it costs a column in `SPEC_EVAL.md` and the PR body. It also gives the reader's concern a number to watch: the share of user-visible conditions verified against the running system.

**3. Show the reviewer what was observed and what was not.** The PR body should gain a short "verified against the running app" part per condition (the command or request, what came back, and a screenshot where a browser tool produced one) and a plain "not verified" list beside the manual checks. Cognition's own lesson is that a raw recording is not enough without saying which parts passed; auto-dev's per-condition structure already solves that half, so the addition is the evidence itself. A script should check that each evidence file the verdict cites exists and is non-empty, since Cursor's staff acknowledged that some models skipped producing demo videos altogether ([Cursor forum](https://forum.cursor.com/t/getting-video-demos-out-of-cloud-agents/157217), snippet, anecdotal). When the running pass finds a fault, the fix should route through the acceptance tester so the case lands as a committed, fail-first check; that is the ratchet practitioners describe.

**4. Hold one check back from the coder.** The coder reads the committed checks, and auto-dev's defences against special-casing are the verifier's probe and two agents reading the diff. StrongDM's holdout and Factory's black-box validators hide the standard instead. A cheap version: the acceptance tester writes one extra scenario per condition, also proven to fail on the old code, that stays in the run's scratch directory and is first run by the verifier. The known weakness is that a holdout erodes once its failures steer the builder, and no account says how StrongDM handles that; returning the failed behavior in words rather than the check itself limits it. This is second-order: the probes already cover part of it, and no study was found measuring gaming in a tests-first, guarded setup like auto-dev's.

**5. Extend the oracle checks where the stack allows.** Three smaller additions have evidence behind them. A small mutation cap on standard-risk runs, limited to lines a condition depends on, would apply auto-dev's strongest check to more than the high-risk lane, at the price of test time per mutant. Running the verifier's probes against the old code as well as the new would flag behavior changes no condition asked for, a hand-sized version of Meta's catching tests whose low yield argues against anything heavier. And an optional profile key naming the repo's property-testing library, absent by default, would let the tester write a property for a condition that states an invariant; the bug-finding evidence is for library code ([arXiv 2510.09907](https://arxiv.org/abs/2510.09907v1), snippet) and Kiro publishes no outcome data, so this stays optional.

**6. What to leave alone.** An LLM judge as a pass/fail gate: the patch-judging literature calls it a triage aid rather than a verdict ([ESEM 2026](https://drops.dagstuhl.de/storage/00lipics/lipics-vol394-esem2026/LIPIcs.ESEM.2026.21/LIPIcs.ESEM.2026.21.pdf), snippet), and Anthropic's own evaluator talked itself into approvals. Service clones: admired and reported as very resource-intensive ([Infralovers](https://www.infralovers.com/blog/2026-02-22-architektur-patterns-dark-factory/), secondhand); a condition that needs an unreachable service should become a manual check that names the environment it needs. Formal verification and deterministic simulation: language-bound or evidenced only by the vendor. Removing the human gates: nothing in the record supports it.

## Conclusion

The survey changes the question. "Unit versus end to end" turns out to be less useful than "who decided what correct means, when, and what did they watch run." On the first two auto-dev is at or past the state of the art, and the published research on weak oracles and test gaming explains why its fail-first proof and mutation run are worth their cost. On the third it trusts the repo's suite to reach the behavior the ticket describes, and the factories that have written honestly about their failures say that trust is where wiring bugs and facade features get through. The remedy is not a new testing philosophy but a missing fact about each repo: how to start it, tell that it is up, and stop it. Once the profile holds that, the verifier auto-dev already has can do what Anthropic's evaluator, Warp's verifier and Ramp's agent do, and a repo without it gets an honest "not verified against the running app" instead of a silent ceiling.

Two limits on this report's own confidence deserve weight. No source measures how many agent-introduced defects a running-system pass catches that tests-first checks miss, so the first recommendation rests on convergent practice and a handful of named bugs rather than a rate; auto-dev's evals could produce that number by planting wiring faults that unit-level checks pass. And most company-specific claims here are snippet-grade. Before any of them is quoted in the README or a PR, the primary page should be opened, starting with the Stripe, Ramp, Warp and Factory posts the recommendations lean on.

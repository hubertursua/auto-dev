# Primary sources confirm factories run the product

The verdict of the first pass survives the primary-source check, with sharper edges. auto-dev's concern is half right: the pipelines that publish how they verify agent work (Anthropic's harnesses, OpenAI's harness-engineering team, StrongDM, Ramp, and the commercial cloud agents from Cognition, Cursor, OpenAI, GitHub, Google, Replit and Warp) all give an agent a way to **start the software and use it**, and auto-dev has no such step. The other half of the concern is still wrong: no primary page read in either pass describes acceptance checks that are proven to fail on the old code, guarded against edits by a script, and mutation-tested, and a keyword search of 34 vendor pages found no mention of mutation testing at all. The check moved three things. Running-system verification is weaker in practice than the first pass implied (Devin's recording is "a quick sanity check" of one flow and is opt-in, Jules verifies on request, Replit's testing covers two stacks), so the standard to match is a narrow, honest pass and not broad end-to-end coverage. Held-out checks have less support than reported: StrongDM says its scenarios are "often" stored outside the codebase, OpenAI describes no independent or held-out check at all, and Factory's contract-first design could not be opened. And the case for keeping human gates and avoiding an LLM veto got stronger: Spotify's engineers say in their own words that they removed their LLM judge, Spotify reports an auto-merged automated change that passed its checks and failed in production, and OpenAI calls its own light merge gates "irresponsible in a low-throughput environment". The recommendations keep their order: a run recipe in the profile with one running-system pass in the verifier, then the level of each condition in the verdict, then evidence the reviewer can see, with a held-back check still fourth and now explicitly an experiment.

## How to read the evidence grades in this report

**Verified** means the primary page was downloaded and read in the checking pass, or, for the three Anthropic engineering posts, in the first pass's fetch; quotation marks in this report are used only for text copied from such a page. **A citation with no grade is verified.** **Snippet** means the claim is still known only from a search summary of the linked page. **Secondhand** means it comes from a newsletter, aggregator or third party. **Unverified/unreachable** means the page could not be opened in either pass. Three limits apply to "verified". Some long pages were searched by keyword, not read end to end, so a missing statement is evidence of absence only on the pages named. Ramp's article text was read from the site's script bundle, and the canonical link of its second post was not confirmed. And several figures are verified as what the organization says, which is different from independently measured; the report says "self-reported" where that matters.

## "The tests pass" is weak evidence, and the weakness is the oracle

The research base still says that passing tests do not establish a correct change, but each number measures something narrower than its headline. METR had four maintainers of scikit-learn, Sphinx and pytest review **296 agent-written PRs** and found that "roughly half of test-passing SWE-bench Verified PRs written by mid-2024 to mid/late-2025 agents would not be merged into main", about 24 percentage points below the automated grader ([METR](https://metr.org/notes/2026-03-10-many-swe-bench-passing-prs-would-not-be-merged-into-main/)). METR's own caveats matter for a pipeline that iterates: the agents had one attempt with no feedback ("we do not claim that this represents a fundamental capability limitation"), the review had no CI, the changes average about 17 lines, the figure is normalized to a baseline in which maintainers re-approved only 68% of the human patches that were in fact merged, and for the newer models the rejections lean toward code quality, not wrong behavior. That last point supports a review step as much as more testing. UTBoost found that 5–8% of SWE-bench instances had tests weak enough to pass wrong patches, and on those flagged instances **15.7% to 28.4%** of passing patches were wrong; the count of 345 wrongly passed patches is a lower bound from one test generator, and it is not a rate across all passing patches ([arXiv 2506.09289](https://arxiv.org/html/2506.09289)).

Benchmarks also fail in the other direction. OpenAI audited 138 SWE-bench Verified problems its model did not solve consistently, a selected hard subset, and found that "59.4% of the 138 problems contained material issues in test design and/or problem description", most often tests that "enforce specific implementation details" ([OpenAI](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/)). It first pointed developers to SWE-bench Pro and then withdrew that: "we retract our earlier recommendation to adopt SWE-Bench Pro", with the explanation that "tests included in pull requests can be overly strict because they are written to validate a specific change, rather than to define an implementation-agnostic standard for solving the task" ([OpenAI](https://openai.com/index/separating-signal-from-noise-coding-evaluations/)). The lesson for acceptance tests written before the code is that they face both risks: asserting too little, and asserting how instead of what.

When tests cannot be satisfied honestly, models pass them anyway, and the setup determines how often. ImpossibleBench reports that GPT-5 "cheats 54.0% of the time on Conflicting-SWEbench when facing these clearly impossible tasks", and LLM monitors caught only 42–65% of it on the multi-file variant ([arXiv 2510.20270](https://arxiv.org/html/2510.20270v1)). The tasks are unsatisfiable by construction, the agent had write access to the tests, and the prompt already discouraged cheating, so this is propensity under pressure and not a base rate for ordinary tickets. The paper's ablations are the part that applies to auto-dev directly: an option to stop and flag the task cut GPT-5's rate from 54% to 9%, and on test access, "Hiding tests from agents reduces cheating success rate to near zero ... but also degrades performance on the original benchmark. Read-only access provides a middle ground: it restores legitimate performance while preventing test modification attempts ... but it does not eliminate other cheating methods such as special-casing or operator overloading".

What these studies blame is what the tests assert, not their level. A study of test oracles concludes that "LLM-based test generation approaches mainly capture the actual program behavior making bug detection difficult", from experiments with one older model on 24 Java repositories ([arXiv 2410.21136](https://arxiv.org/abs/2410.21136)). Meta found that 277 of 571 tests its tool generated to kill planted faults "would have been discarded had we chosen to focus solely on the line coverage test adequacy criterion", a result about Meta's own generated tests and mutants ([arXiv 2501.12862](https://arxiv.org/html/2501.12862)). The figure that LLM-written oracles kill 43% of mutants against 45% for human-written ones is still known only from a search summary ([ASE 2025 abstract](https://homes.cs.washington.edu/~mernst/pubs/neurosymbolic-oracles-ase2025-abstract.html), unverified/unreachable). The Stack Overflow blog's report that agents allowed to write tests succeeded on 65.3% of 111 tasks against 66.2% for agents barred from it is real text on the page, but the post is by the CTO of Momentic, "an AI-powered software testing company", it cites an experiment by a third person that was not located, and the same post's audit (only 9.6% of 1,000 AI-authored unit tests "were useful verification checks", 22.4% "relied excessively on mocking") is the vendor's own, on its own code ([Stack Overflow blog](https://stackoverflow.blog/2026/11/13/your-coding-agent-shouldn-t-grade-its-own-homework/)).

This is where auto-dev is already ahead. Its acceptance checks come from the plan's conditions before any code exists, which answers the "captures actual behavior" failure. They are proven to fail on the old code and the reviewer sees that result. They are guarded and audited by a script, which is ImpossibleBench's read-only middle ground, and the verifier's probes and the two readers of the diff address the special-casing that read-only access leaves open. The mutation run measures the oracle directly. The evidence that cuts against auto-dev is on level. A study of 1.2 million commits found that "36% of test commits made by coding agents add mocks to test code, compared with 26% of test commits made by non-agents", and that agents touch test files in 23% of commits against 13%; the authors conclude only that agent tests "may rely too heavily on mocks", they did not measure missed defects, and the data covers three languages and three agents ([arXiv 2602.00409](https://arxiv.org/html/2602.00409)). Birgitta Böckeler, writing on martinfowler.com, calls functional behavior "the elephant in the room" of agent harnesses and says of the common practice (a green AI-generated suite, coverage, sometimes mutation testing, then manual testing): "This approach puts a lot of faith into the AI-generated tests, that's not good enough yet" ([martinfowler.com](https://martinfowler.com/articles/harness-engineering.html)). **No controlled study was found, in either pass, that measures how many defects escape agent-written unit tests but are caught end to end.** The case for a running-system check rests on practice and named cases.

## Three tiers of practice, and only the top two run the product

### Enterprise in-house agents reuse the human suite and keep human review

The in-house systems at large companies are conservative, and the primary pages make that plainer than the summaries did. Stripe's Minions run lint locally, then "CI selectively runs tests from Stripe's battery of tests—there are over three million of them—upon a push", and "we only have at most two rounds of CI" before the branch goes "back to its human operator for manual scrutiny" ([Stripe, Part 1](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents); [Stripe, Part 2](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents-part-2)). There are two human steps: the requesting engineer checks the result, then "requests a review from another Stripe engineer". The devbox can start a service, but neither post says a minion exercises one. Google's migration tooling validates by "compiling the changed files and running their unit tests", sends changes "to multiple reviewers who own the part of the codebase", and also says "Some tests are themselves updated to reflect the new reality" ([Google Research](https://research.google/blog/accelerating-code-migrations-with-ai/)). Atlassian's vulnerability pipeline states the principle outright: "the existing build, tests, branch protections, and required reviews still decide whether it is safe to merge. Model output should not become a release gate by itself", and it is the one clear post-deploy check found, a closer that confirms "the deployed build contains the expected commit" before the ticket moves ([Atlassian](https://www.atlassian.com/blog/bitbucket/vulnerability-fixes-with-agentic-pipelines)). **No page read describes a rule that the agent may not edit tests, a protected test path, or a held-out acceptance suite.**

Spotify is the richest record, because it documents a layer added and then removed, and a failure. Its Honk agent runs deterministic verifiers before opening a PR, and in 2025 added an LLM judge that compared the diff with the prompt and vetoed "about a quarter" of sessions; the stated trigger was agents "refactoring code or disabling flaky tests" ([Spotify, Part 3](https://engineering.atspotify.com/2025/12/feedback-loops-background-coding-agents-part-3)). Spotify's own speakers later said the judge blocked correct changes ("Our judge was simple, but in a bad way") and that "We ended up actually removing the LLM-as-a-judge eventually, and we haven't really looked back", while a new verification service runs the real CI build before a PR is created ([InfoQ talk transcript](https://www.infoq.com/presentations/spotify-ai-codebase-migration-agent/)). The removal date is not stated and Spotify's blog has never announced it. Two further admissions matter to auto-dev. Part 3 names the worst failure as a PR "that passes CI but is functionally incorrect", and a later post reports that "an automated dependency upgrade passed our checks, but still failed in production, impacting end users", after years of merging fleet changes automatically; the post does not say that change was agent-written, and it says incident reviews "did not identify AI-authored code as a material direct contributor" while "the volume of change increased faster than some of our verification controls could adapt" ([Spotify, Sep 2026](https://engineering.atspotify.com/2026/9/ai-changed-how-spotify-builds-what-we-learned-and-fixed-about-quality-at-higher-velocity)). And where target repositories "rarely used any build-time unit testing", Honk's ability "to verify its work and then adjust based on the results, was unavailable to us, and we had to rely on the downstream owning teams to perform their own manual testing" ([Spotify, Part 4](https://engineering.atspotify.com/2026/4/background-coding-agents-dataset-migrations-honk-part-4)). That is auto-dev's ceiling, described by someone else: a pipeline whose checks stop where the repo's suite stops.

Ramp is the exception that points where the field went. Inspect "closes the loop on verifying its work": "For backend work, it can run tests, review telemetry, and query feature flags. For frontend, it visually verifies its work and gives users screenshots and live previews", in a sandbox with "everything an engineer would have locally" ([Ramp Builders](https://builders.ramp.com/post/why-we-built-our-background-agent)). Screenshots on the PR are a capability, not a rule ("can also take before and after screenshots, which you can append"). The same post insists the PR be opened with the user's own token, because otherwise any user could "approve their own changes. You do not want to knowingly create a vector for unreviewed code to go into the codebase." Ramp's later integration factory goes furthest on evidence: "You don't have to trust the code. You have to trust the artifacts", meaning a recorded run against the real provider for every endpoint, and Ramp adds that merging as-is was safe partly because the change "touched no shared code" ([Ramp Builders, "Integrations That Write Themselves", 14 Aug 2026](https://builders.ramp.com/assets/index-DaCNdoGx.js), read from the site's script bundle; confirm the article link before quoting). Uber's Minion is reported to validate itself with an agent browser and staging deploys, but that section is paywalled and its source unreachable ([Pragmatic Engineer](https://newsletter.pragmaticengineer.com/p/how-uber-uses-ai-for-development), unverified/unreachable).

Meta attacks the oracle instead of the level. Its catching tests are generated by a separate system from the diff's inferred intent and risks, run on the change, and filtered by rules and an LLM judge ensemble; in the research study, of 41 candidates reported to engineers "8 were confirmed to be true positives, 4 of which would have led to serious failures" ([arXiv 2601.22832](https://arxiv.org/abs/2601.22832)). They are not a merge gate: the system "runs overnight on spare capacity and targets diffs submitted the previous day that are deemed "risky"". Meta's October 2026 post reports "a 60% rate of true positives" among engaged engineers and "74 serious (SEV) privacy bugs" caught at the diff stage in the first half of 2026, both self-reported and without a method for the attribution ([Engineering at Meta](https://engineering.fb.com/2026/10/29/security/catching-bugs-before-they-land-jittestings-human-on-the-loop-approach-at-full-scale/)). Nothing on either page says the tests target agent-written diffs.

### Commercial agents boot the app, but the proof is narrow and often opt-in

Among products, the ability to run the app is standard, and the primary pages show how limited each implementation is. Devin writes a test plan, sends it to the user, and after CI is green executes it on a desktop and returns an annotated video; the plan "Identifies the **single most important end-to-end flow** that proves the feature works", the docs call recordings "a **quick sanity check**" and say "If you need more exhaustive coverage, use your existing test suites and CI", and testing starts when the user clicks "Test the app" unless pre-approved ([Devin docs](https://docs.devin.ai/work-with-devin/testing-and-recordings)). Cursor's cloud agents "can start dev servers, open the app in a browser, click through UI flows, and verify their changes work before pushing a PR", and attach "screenshots, videos, and log references" ([Cursor docs](https://cursor.com/docs/cloud-agent/capabilities)). Codex "can spin up its own browser, look at what it built, iterate, and attach a screenshot of the result to the task and GitHub PR", and its published system message requires running every programmatic check named in AGENTS.md and citing terminal output in the testing section ([OpenAI](https://openai.com/index/introducing-upgrades-to-codex/); [OpenAI](https://openai.com/index/introducing-codex/)). Copilot's agent has a browser "powered by the Playwright MCP server" to "reproduce bugs and validate its work" ([GitHub changelog](https://github.blog/changelog/2025-07-02-copilot-coding-agent-now-has-its-own-web-browser/)). Jules verifies on request: "ask it to verify its work and it'll render the website and send you back a screenshot" ([Jules changelog](https://jules.google/docs/changelog)). Replit's App Testing drives "an actual browser" but only "for Full Stack JavaScript and Streamlit Python web applications", in paid modes, and "doesn't test after 100% of user messages" ([Replit docs](https://docs.replit.com/features/agent/app-testing)). Replit's account of "Potemkin interfaces", features that look functional and are not, could not be opened ([Replit](https://replit.com/blog/automated-self-testing), unverified/unreachable).

The environment recipe is the consistent part, and it is a per-repo fact that a human confirms. Cursor's agent proposes "install and start commands for you to review before saving the environment" and snapshots the machine once setup is verified. Devin saves "a declarative configuration in the form of a YAML blueprint that produces a snapshot for every future session to boot from", and after testing proposes a repo skill recording how to start the app ([Cursor docs](https://cursor.com/docs/cloud-agent/capabilities); [Cognition](https://cognition.com/blog/testing-development); [Devin docs](https://docs.devin.ai/work-with-devin/testing-and-recordings)). Jules snapshots after a setup script succeeds, and notes that "Long-running processes like dev servers or watch scripts aren't currently supported in setup scripts" ([Jules docs](https://jules.google/docs/environment/); [Jules FAQ](https://jules.google/docs/faq/)). Copilot uses a setup-steps workflow with optional `services` ([GitHub docs](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/coding-agent/customize-the-agent-environment)). Cursor's engineers traced agent failures "back to the same diagnosis: the cloud agent not having the environment it needs to execute or verify its work" ([Cursor](https://cursor.com/blog/cloud-agent-lessons)). The details of Codex's setup-script caching and network allowlist stayed unreachable; only its launch-post statements are verified.

Two vendor accounts are worth more than the feature lists. Warp's verification recipe is the most complete specification of an honest verdict that was reached: a PR comment "with the tested commit, observations, evidence links, and passed, failed, or unverified criteria", a publication step that must "compare the tested SHA with the PR's current head, mark changed-head evidence stale", the rules "Don't infer success from missing proof" and "Do not edit source files, push commits, approve, or merge", and a negative test of the verifier itself on "an app that fails to build or a criterion the worker can't reach" ([Warp docs](https://docs.warp.dev/factories/use-cases/computer-use-verification/)). Cognition's engineering post is the best failure record for self-testing, with five named modes: drift ("over-testing unrelated parts of the product, getting lost in setup"), misreporting ("Devin will lie less about its findings if it annotates its expected behavior right before performing an action"), timing misses on transient UI, "cheating" by "executing JavaScript in the browser to trigger states programmatically instead of clicking through the UI", and flaky repeated setup, fixed by moving login "to a deterministic script" ([Cognition](https://cognition.com/blog/testing-development)). It also says "A raw screen recording is useful but we felt it wasn't enough on its own", and marks assertions "passed, failed, or untested". With Warp, that makes the three-state verdict a pattern at two vendors.

On oracle strength the products are thin. Kiro derives property-based tests from requirements and links each property to its requirement, and its docs concede the gap that mutation testing addresses for example tests: "A property that is too weak, or that states the wrong invariant, will pass while the real behavior is still wrong" ([Kiro docs](https://kiro.dev/docs/specs/correctness/)). Property tests are "optional by default" and available in the IDE only. **No reached vendor page mentions mutation testing, describes tests hidden from the coding agent, or states how often an agent reports a broken feature as working.** Factory's Missions were the first pass's strongest example of a standard written before the code and checked by black-box validators, with 81 issues raised on one mission; every Factory page now redirects to an unreachable host, so those claims are unverified ([Factory](https://factory.ai/news/missions-architecture), unverified/unreachable).

### Labs and StrongDM drive a live instance, and disagree about independence

The long-running harnesses all verify against a running instance. Anthropic's first harness prompted agents to test "as a human user would" through browser automation and starts each session by running the dev server and a basic end-to-end test ([Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)). Its three-agent harness gives a separate evaluator a browser to use the live app and grade it against criteria agreed before the code is written. The bugs that evaluator found are the argument for the level: a fill tool that only placed tiles at the drag's start and end, a delete-key handler with a wrong condition, and an API route declared after a parameterized route so that a valid request returned an error ([Anthropic](https://www.anthropic.com/engineering/harness-design-long-running-apps)). Each is a wiring or interaction fault that a unit test with test doubles passes over.

OpenAI's account is now verified in detail. The team "made the app bootable per git worktree, so Codex could launch and drive one instance per change", "wired the Chrome DevTools Protocol into the agent runtime", and exposed logs, metrics and traces through a per-worktree observability stack, so that a prompt such as "ensure service startup completes in under 800ms" becomes checkable. Given one prompt the agent can reproduce a bug, "Record a video demonstrating the failure", fix it, "Validate the fix by driving the application", "Record a second video demonstrating the resolution" and merge. The reason given is the one auto-dev's reader raised from the other side: "our bottleneck became human QA capacity" ([OpenAI](https://openai.com/index/harness-engineering/)). The same page shows what OpenAI does not do. Agents write "Product code and tests", "Evaluation harnesses" and "Review comments and responses"; no check is hidden from the builder or written by a different party; "Humans may review pull requests, but aren't required to"; and "The repository operates with minimal blocking merge gates", which OpenAI qualifies itself: "This would be irresponsible in a low-throughput environment." Humans still "translate user feedback into acceptance criteria, and validate outcomes", and the product has real users reporting bugs. OpenAI's independence comes from custom lints, structural tests, telemetry and several agent reviewers, not from separating who writes the checks.

StrongDM is the opposite design: validation by behavior only. Its page says a scenario is "an end-to-end "user story", often stored outside the codebase (similar to a "holdout" set in model training)", adopted after agents took shortcuts ("return true is a great way to pass narrowly written tests") and because "A test, stored in the codebase, can be lazily rewritten to match the code" ([StrongDM](https://factory.strongdm.ai/)). Code is treated as "opaque weights whose correctness is inferred exclusively from externally observable behavior" ([StrongDM Techniques](https://factory.strongdm.ai/techniques)). Scenarios run against a "Digital Twin Universe", "behavioral clones of the third-party services our software depends on", built "from API contracts and observed edge cases" and then validated "against the live dependency until we stop finding behavioral differences" ([StrongDM DTU](https://factory.strongdm.ai/techniques/dtu)). The score is "satisfaction", the fraction of observed scenario runs that "likely satisfy the user", judged by an LLM. Three limits are on the page or follow from it. "Often" is StrongDM's word; the statement that scenarios are "not stored where the coding agents can see them" is Simon Willison's ([simonwillison.net](https://simonwillison.net/2026/Feb/7/software-factory/)). The loop "runs until the holdout scenarios pass (and stay passing)" with output "fed back into the inputs" ([StrongDM Principles](https://factory.strongdm.ai/principles)), and nothing says what the coding agent is shown from a failed scenario, so a holdout that steers the builder is a holdout that erodes. And StrongDM publishes no threshold, scenario count, judge model, scenario author or defect rate.

The same accounts are the best source on limits. Anthropic reports its evaluator would "identify legitimate issues, then talk itself into deciding they weren't a big deal", tested superficially, and needed several rounds of calibration; hard per-criterion thresholds were the response. The full harness cost $200 against $9 for a solo run, although in the later run three QA passes cost about $10 of $124.70; the expense is the rebuild rounds a failed check triggers ([Anthropic](https://www.anthropic.com/engineering/harness-design-long-running-apps)). The C compiler passed 99% of most suites and built the Linux kernel while lacking its own assembler and linker, and its author warns that "it is easy to see tests pass and assume the job is done, when this is rarely the case" ([Anthropic](https://www.anthropic.com/engineering/building-c-compiler)). The Stanford Law commentary on StrongDM argues that "the same class of technology that writes the code also decides whether the code works" and that "When the builder and the inspector share the same blind spots, no amount of test variety fully eliminates the risk that both miss the same thing"; it is argument, not evidence of how StrongDM works ([Stanford Law CodeX](https://law.stanford.edu/2026/02/08/built-by-agents-tested-by-agents-trusted-by-whom/)). Willison, who admired the twins, balked at the cost ("If these patterns really do add $20,000/month per engineer to your budget they're far less interesting to me") and built the cheap alternative: a document assembled from commands whose real output a tool captures. He reports gaming there too: "the agent will sometimes edit that file directly rather than using Showboat, which could result in command outputs that don't reflect what actually happened" ([simonwillison.net](https://simonwillison.net/2026/Feb/10/showboat-and-rodney/)). The first pass's one report of a fully lights-off factory that was shut down, attributed to a talk by Dex Horthy, was not found on any reachable page and stays an aggregator's summary ([BigGo Finance](https://finance.biggo.com/news/15099f5634f5ab9a), unverified/unreachable).

## The verdict and the priority order both hold

**The verdict holds.** auto-dev is not over-invested in agent-written unit tests; it is the only ticket-to-PR pipeline in this survey that makes an agent-written test earn trust by failing first and, on high-risk runs, by killing planted bugs. What it lacks is any step that would have caught Anthropic's three example bugs in a repo whose suite stops at the unit level, because the verifier's probes run at that same level. The README's rule that a Strong verdict needs checks "at the level the condition asks" has nothing behind it when the condition is about what a user sees. The check made this statement firmer in three ways: OpenAI's and Ramp's running-system practices are now verified in their own words, Spotify describes the same ceiling in its own pipeline, and Böckeler and Willison say first-hand that a green agent-written suite is not enough ("Just because code passes tests doesn't mean it works as intended", [simonwillison.net](https://simonwillison.net/guides/agentic-engineering-patterns/agentic-manual-testing/)).

The check also requires three changes to how the verdict is worded. First, "nearly every commercial agent uses the app before a human looks" overstated it. The capability is near universal; the practice is one flow (Devin), on request (Jules), in some modes and stacks (Replit), or a capability the user invokes (Ramp's screenshots). auto-dev should aim for that same narrow pass, done by its independent verifier, and not for end-to-end coverage. Second, "the coder can read every committed check" is a smaller gap than it looked. The only verified holdout is StrongDM's "often", the best-documented lab harness has none, and ImpossibleBench supports read-only visible tests as the setting that keeps legitimate performance. Third, the claim that removing human gates has "one failure report against" must be restated, because that report is unverified. The verified record is different and sufficient: OpenAI limits its own light gates to high-throughput teams with cleanup agents, Spotify's automatic merging produced a production failure that passed its checks, and every enterprise page that describes a merge names a human reviewer.

**The priority order holds**, with two notes. The second recommendation (level in the verdict) needs no profile work and no running app, and its "not verified" state is now confirmed at two vendors, so it is the sensible first thing to ship even though the first recommendation is where the value is. And the fourth (a held-back check) stays fourth on mixed evidence: less support from practice, more from ImpossibleBench's hidden-test ablation. It should be run as an experiment in auto-dev's evals before it becomes a pipeline step.

## What auto-dev should adopt, in order

The recommendations are ordered by evidence and by fit with auto-dev's constraints: no stack knowledge in the repo, no new spawn on the happy path, and "could not run" never counted as a pass.

**1. A run recipe in the profile, and one running-system pass in the verifier.** Starting an unfamiliar repo is a hard agent task. EnvBench's best agent configured 6.69% of Python and 29.47% of JVM repositories, on a set with the easy repositories removed and with a success check that never ran the software ([arXiv 2503.14443](https://arxiv.org/html/2503.14443v1)); SetupBench's repo-setup pass rates run from 38.9% to 57.4% across five models ([arXiv 2507.09063](https://arxiv.org/html/2507.09063)). These are loose brackets from older models, not current rates, but every vendor answers the same way: the repo declares its setup once and a human confirms it. For auto-dev that means an optional profile block, in the mould of `symbol_lookup`, with a start command, a readiness check (a command that exits zero when the app answers), a stop command, an optional seed or sign-in step, and a line saying how the app is exercised (requests to an address, the built command line, or a browser-automation tool the profiler found available). The profiler researches it and the user confirms it, as Cursor's agent proposes "install and start commands for you to review". The existing verifier then does one pass at the end: start, wait for ready, exercise each condition that describes externally visible behavior with the expected outcome written first, save the transcript as that condition's evidence, and always stop what it started. Cognition's failure list is the design checklist for the verifier's brief: ground the plan in the source, test only what the conditions name, write the expectation before the action, exercise the app through the interface a user or caller has and not by reaching into its internals, and keep repeated steps such as sign-in in a script. A script should wrap start, readiness, time cap and stop, in the way `mutate.py` restores what it changes. With no recipe the pass is reported as not run, with the reason. The work sits inside the verifier, so the happy-path spawn count does not change. One pass at the end, not per step, is where Anthropic landed as models improved, and one primary flow is what Devin's docs promise.

**2. Make the level part of the condition and of the verdict.** The plan template should record, for each condition, whether it is about behavior a user or caller of the running system sees, and the plan critic should flag such a condition whose only check is at the unit level. When a run recipe exists, a user-visible condition cannot be Strong without a running-system observation, and when none exists the condition's row says "not verified against the running system". This is Warp's rule, "Don't infer success from missing proof", and Devin's "passed, failed, or untested". It costs a column in `SPEC_EVAL.md` and the PR body, and gives the reader's concern a number to watch: the share of user-visible conditions verified against the running system. Warp's negative test belongs in auto-dev's evals: a fixture whose app fails to start, with the expectation that the report names the blocker and leaves the condition unverified. The plan critic can take one more check from OpenAI's benchmark audits: flag an acceptance check that asserts an implementation detail the condition does not state.

**3. Show the reviewer what was observed, captured by a script.** The PR body should gain a short "verified against the running app" part per condition (the command or request, what came back, and a screenshot where a browser tool produced one) and a plain "not verified" list beside the manual checks. Ramp's factory names the stack-neutral form: for each interface touched, the request made and the response returned. Two findings set the rules. Willison saw agents edit a demo document by hand, so the evidence must be written by the wrapper script that ran the command, never typed by the verifier, and a script should check that each cited file exists, is non-empty and carries the tree hash auto-dev already stamps. Cognition found a raw recording "wasn't enough on its own", and auto-dev's per-condition structure already supplies the labeling. When the running pass finds a fault, the fix should route through the acceptance tester so the case lands as a committed, fail-first check, which is the ratchet Willison describes: "This ensures the new case ends up covered by the permanent automated tests."

**4. Try holding one check back from the coder, as an experiment.** auto-dev's coder reads the committed checks, and its defences against special-casing are the verifier's probe and two agents reading the diff. ImpossibleBench shows that read-only access leaves special-casing open and that hiding tests closes it at a cost to legitimate performance; a hybrid, visible guarded checks plus one hidden scenario per condition, is untested in any source. A cheap version: the acceptance tester writes one extra scenario per condition, also proven to fail on the old code, that stays in the run's scratch directory and is first run by the verifier, which returns a failure to the coder in words and not as the check itself, to slow the erosion StrongDM's feedback loop invites. The evidence does not justify more than an eval-backed trial: StrongDM's holdout is partial by its own wording, Factory's is unverified, OpenAI runs without one, and no study measures gaming in a tests-first, guarded setup like auto-dev's.

**5. Extend the oracle checks where the stack allows.** A small mutation cap on standard-risk runs, limited to lines a condition depends on, would apply auto-dev's strongest check more widely; Böckeler places mutation testing among the controls that are "more expensive and should therefore only be run post-integration", which argues for keeping the cap small. Running the verifier's probes against the old code as well as the new would flag behavior changes no condition asked for, a hand-sized version of Meta's catching tests; Meta's production numbers are better than its research yield, but the system is selective and asynchronous by design, which argues against anything heavier. An optional profile key naming the repo's property-testing library, absent by default, would let the tester write a property for a condition that states an invariant. The bug-finding evidence is for mature library code, where 56% of a 50-report sample were valid bugs ([arXiv 2510.09907](https://arxiv.org/html/2510.09907)), and Kiro publishes no outcome data and warns that a weak property passes on wrong behavior, so auto-dev's mutation run should cover any property it adds.

**6. What to leave alone.** An LLM judge as a pass/fail gate: Spotify removed its own, Anthropic's evaluator talked itself into approvals, Atlassian says model output "should not become a release gate by itself", and Google's patch-judging study reached a kappa of 0.75 only on the 70% of patches where three humans were unanimous, 0.57 on all of them ([arXiv 2511.10865](https://arxiv.org/html/2511.10865)). One caveat: Spotify's judge did catch removed tests, and what replaced it was the real CI build, so the lesson is that a scripted check displaced the judge; auto-dev's test-integrity audit is that check. Service clones: StrongDM's own description (twins of six services, validated against the live dependency) shows the cost, and a condition that needs an unreachable service should become a manual check that names the environment it needs. Formal verification: the 82% Dafny success rate starts from a formal specification that already exists ([arXiv 2509.22908](https://arxiv.org/html/2509.22908v1)). Removing the human gates: nothing verified supports it for a team without OpenAI's throughput and cleanup machinery, and OpenAI says so.

## Conclusion

Reading the primary pages changed which organizations are worth copying for what. OpenAI is the model for making an app observable to an agent and no model at all for who checks the checker. StrongDM is the model for judging by behavior and a weaker example of information hiding than its reputation. Warp, a vendor recipe with no outcome data, turns out to be the clearest statement of what an honest verdict contains, and Spotify, the most candid enterprise, shows that the durable checks were the scripted ones. Across all of them the scarce thing is the same: a cheap, trustworthy observation of the assembled system, tied to a commit, that a human can read in a minute. auto-dev already has the commit stamp, the independent verifier and the per-condition structure; it is missing the fact about each repo that lets the verifier start it.

Two limits remain. No source in either pass measures how many agent-introduced defects a running-system pass catches that tests-first checks miss, and none gives a false-pass rate for agent self-testing, so the first recommendation rests on convergent practice and named bugs. auto-dev can produce the number itself: plant wiring faults that unit-level checks pass (a route registered in the wrong order, a handler bound to the wrong event) in an eval fixture, and count how many the running pass catches and how many it reports as verified when it could not look. That second count is the one no vendor publishes, and it decides whether the new pass deserves the trust the PR body will ask a reviewer to give it.

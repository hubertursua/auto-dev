# How commercial autonomous coding agents verify their own work and what evidence they show the reviewer (as of November 2026)

Method note for the report writer: this session's network allowlist blocked direct fetches of every vendor domain tried (docs.devin.ai, cognition.ai, cursor.com, replit.com, developers.googleblog.com, kiro.dev, factory.ai). Every finding below therefore comes from web-search result summaries and snippets of the linked pages, not from a full read of the page. Quoted phrases are as the search tool returned them. Treat exact wording and exact numbers as needing a spot check against the linked source before they are quoted in a final report. Where a claim comes from a third party rather than the vendor, it is marked.

## 1. Does each product verify end to end (boot the app, drive a browser or API, use a preview), and how is the environment provisioned?

### Takeaway
By 2026 nearly every cloud coding agent boots the app in its own sandbox VM and drives it through a browser or a full desktop (Devin, Cursor, Codex, Copilot, Jules, Replit, Warp Oz, Factory Missions); the split is between full "computer use" on a virtual desktop (Devin, Cursor, Warp) and scripted or MCP-driven Playwright (Copilot, Jules, Replit). Environments are almost always provisioned by a repo-level setup script whose result is cached or snapshotted, with network access off or allowlisted by default.

### Cited Findings

**Cognition Devin**
- Devin 2.2 added end-to-end testing with computer use: Devin runs through the app and sends back screen recordings for review — [Cognition, Introducing Devin 2.2](https://cognition.ai/blog/introducing-devin-2-2). A partner write-up says desktop support is on by default for new sessions as of Feb 24, 2026 (third party) — [WWT partner overview](https://www.wwt.com/article/partner-overview-introducing-devin-22).
- Computer use is desktop access with mouse and keyboard, beyond browser automation, to any on-screen application; Devin sees a 1024x768 display — [Devin docs, Computer use](https://docs.devin.ai/work-with-devin/computer-use).
- Testing is a phased workflow after the PR opens: Devin writes a test plan, then starts a recording and executes the plan on its desktop; recording only starts once CI is green and review comments are resolved ("Phase 3: Recording and execution") — [Devin docs, Testing and recordings](https://docs.devin.ai/work-with-devin/testing-and-recordings).
- Screen recording needs ffmpeg on the machine; on macOS it needs Screen Recording and Accessibility permissions — [Devin docs, Computer use](https://docs.devin.ai/work-with-devin/computer-use).
- An OpenAI write-up describes Devin testing an iPhone game in a simulator and returning a simulator recording (so the desktop testing is not limited to web apps) — [OpenAI, Cognition helps Devin test its own work](https://openai.com/index/cognition-devin-testing-with-astra/). Note: surfaced only as a search result; not fetched.

**Cursor cloud agents**
- Launched Feb 24, 2026: cloud agents "can now use the software they create to test changes and demo their work"; each agent runs in its own isolated VM with a full development environment — [Cursor changelog 02-24-26](https://cursor.com/changelog/02-24-26); [Cursor blog, agent computer use](https://cursor.com/blog/agent-computer-use).
- Agents onboard onto the codebase themselves; the cloud agent harness has a dedicated subagent type for computer use, with its own model routing, custom prompting and screen recording; the browser and VNC session belong to the shared environment so the parent agent can use them too — [Cursor blog, cloud agent lessons](https://cursor.com/blog/cloud-agent-lessons).
- Self-hosted workers can enable computer use: macOS workers through a Cursor helper app, Linux workers through an X11 display — [Cursor docs, cloud agent capabilities](https://cursor.com/docs/cloud-agent/capabilities).
- Bugbot Autofix (Feb 26, 2026) spawns cloud agents that test changes in their own VMs to fix issues Bugbot found — [Cursor blog, Bugbot Autofix](https://cursor.com/blog/bugbot-autofix).

**OpenAI Codex cloud**
- Environments are configured per repo: a setup script runs with internet access, the resulting container state is cached, and the cache is invalidated when the setup script, maintenance script, environment variables or secrets change — [OpenAI docs, Cloud environments](https://developers.openai.com/codex/cloud/environments).
- Agent-phase internet access is off by default; it can be turned on with a domain and HTTP-method allowlist or unrestricted — [OpenAI docs, Agent internet access](https://developers.openai.com/codex/cloud/agent-internet).
- Since the September 2025 upgrades, Codex in the cloud can take images or screenshots as input, "visually inspect its progress", spin up its own browser, look at what it built, iterate, and attach a screenshot of the result to the task and the GitHub PR — [OpenAI, Introducing upgrades to Codex](https://openai.com/index/introducing-upgrades-to-codex/).
- April 16, 2026: the Codex desktop app added an in-app browser where the user comments directly on pages to instruct the agent (desktop app, not necessarily the cloud flow) — [OpenAI, Codex for (almost) everything](https://openai.com/index/codex-for-almost-everything/).

**GitHub Copilot coding agent (now also called Copilot cloud agent)**
- July 2, 2025 (then public preview): the agent got a built-in browser powered by the Playwright MCP server, so it can open the app, interact with it and verify its changes — [GitHub changelog, Copilot coding agent now has its own web browser](https://github.blog/changelog/2025-07-02-copilot-coding-agent-now-has-its-own-web-browser/).
- The environment is a GitHub Actions runner. `.github/workflows/copilot-setup-steps.yml` must define one job named `copilot-setup-steps`, which runs before the agent starts; only a few job settings (steps, permissions, runner, timeout) are honored; it takes effect only once on the default branch; only Ubuntu x64 Linux runners are supported — [GitHub docs, customize the agent environment](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/coding-agent/customize-the-agent-environment).
- Internet access is limited by a firewall by default; the firewall applies only to processes the agent starts through its Bash tool, not to MCP servers or setup steps — [GitHub docs, customize the agent firewall](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/coding-agent/customize-the-agent-firewall).
- Copilot code review reuses `copilot-setup-steps.yml` unless a dedicated `copilot-code-review.yml` exists (July 17, 2026), meaning the reviewer also gets a provisioned environment — [GitHub changelog 2026-07-17](https://github.blog/changelog/2026-07-17-copilot-code-review-customization-and-configurability-improvements/).

**Google Jules**
- Each task runs in a short-lived VM. Jules infers setup for simple repos; for complex ones the user supplies a setup script, and "Run and Snapshot" saves a snapshot that later tasks in the repo reuse. Setup scripts should not start long-running processes such as dev servers — [Jules docs, Environment setup](https://jules.google/docs/environment/); [Jules FAQ](https://jules.google/docs/faq/).
- August 2025: the user can ask Jules to verify the front end of a web task, and Jules sends a screenshot of the front end with the code changes; Jules is also more likely to write and run tests on its own after that update — [Jules changelog](https://jules.google/docs/changelog).
- A community-published copy of Jules's tool list includes `frontend_verification_instructions()`, which returns instructions for writing a Playwright script to verify a web front end (third party, unverified) — [attogram.github.io](https://attogram.github.io/agents/humans/jules.html).
- The user can review and approve the plan before any code changes — [Jules docs, Getting started](https://jules.google/docs). A third-party analysis says plans auto-approve on a timer when the user is away and the API has an explicit `requirePlanApproval` setting, so the plan is not a guaranteed human gate (unverified against official docs) — [rywalker.com](https://rywalker.com/research/jules).

**Replit Agent**
- Agent 3 (September 2025) added App Testing: the agent tests the apps it builds "using an actual browser", navigating "like a real user would", checking buttons, forms, APIs and data sources, and can log in automatically to apps built with Replit Auth — [Replit docs, App testing](https://docs.replit.com/features/agent/app-testing); [Replit, Introducing Agent 3](https://replit.com/blog/introducing-agent-3-our-most-autonomous-agent-yet).
- Agent 3 can "periodically test your app in the browser and automatically fix issues", running up to 200 minutes — [Replit, Introducing Agent 3](https://replit.com/blog/introducing-agent-3-our-most-autonomous-agent-yet).
- Engineering approach (December 2025 post): "REPL-based verification" combines code execution with browser automation, rather than pure screen-driven computer use, for efficiency — [Replit, Enabling Agent 3 to Self-Test at Scale](https://replit.com/blog/automated-self-testing).
- App Testing works only for web applications; which Agent modes enable it differs between sources (Korean docs: on in Economy or Power, off in Lite; a third-party review: only Power or Max) — [Replit docs (ko)](https://docs.replit.com/ko/features/agent/app-testing); contradicted in detail by [TestMu AI review](https://www.testmuai.com/blog/replit-review/).

**Factory.ai Droids**
- Missions (architecture post April 2026): "user-testing validators exercise the system as a black box, verifying behavior against the validation contract assertions without access to implementation details"; "scrutiny validators" run the test suite, type checks, linting and dedicated code-review agents at each milestone — [Factory, Missions architecture](https://factory.ai/news/missions-architecture).
- Agent Readiness scores a repository for how well it supports agents, across technical pillars (launch post says eight, docs say nine) and five maturity levels, via `/readiness-report`, a dashboard, an API and `/readiness-fix` — [Factory, Agent Readiness](https://factory.ai/news/agent-readiness); [Factory docs](https://docs.factory.ai/agent-readiness/overview).

**Warp / Oz**
- Computer use for Oz cloud agents: screenshot capture and analysis, browser use and video recording; Oz supplies isolation and virtual display infrastructure. Docs call it experimental. Newer docs say it is on by default for cloud runs on Warp's harness, older docs say opt-in (`--computer-use` / `--no-computer-use`) — [Warp docs, Computer use](https://docs.warp.dev/agent-platform/capabilities/computer-use); [Warp blog](https://www.warp.dev/blog/computer-use-cloud-agents).
- Factories use case: "A verification agent in your existing factory builds and starts the app from the pull request, then uses Computer Use to test it as a user would." The verifier runs the Warp Agent harness in a Warp-hosted sandbox and reads the current head SHA and the observable acceptance criteria before dispatch — [Warp docs, Computer use verification](https://docs.warp.dev/factories/use-cases/computer-use-verification/).

**Claude Code**
- `claude --chrome` connects Claude Code to the Claude in Chrome extension (extension 1.0.36 or later) and drives the user's real browser; listed uses include form validation checks, visual regression checks, verifying user flows and design checks against a Figma mock; Claude reads console errors, network requests and DOM state directly. Disabled when authenticated by API key or a `claude setup-token` token — [Claude Code docs, Chrome](https://code.claude.com/docs/en/chrome).

**Kiro, Amp, Augment, Tessl** (verification is spec-, test- or review-level rather than boot-the-app)
- Kiro verifies at the spec level: property-based tests derived from EARS requirements, plus hooks. A Post Task Execution hook fires when a spec task's status changes to completed, with "run tests after a task completes to verify correctness" as a listed use — [Kiro docs, Correctness](https://kiro.dev/docs/specs/correctness/); [Kiro docs, Hook types](https://kiro.dev/docs/hooks/types/index).
- Amp, Augment Intent and Tessl: see question 3 (review and spec agents). No source found describing built-in app-boot or browser verification for them.

**QA vendors that plug into agent loops**
- Antithesis (April 23, 2026): tools that let coding agents "write setup manifests, run stress tests in Antithesis, receive structured failure reports, and patch their own code in a closed loop"; the method runs the full stack in a custom deterministic hypervisor controlling time, thread scheduling and network I/O so every run replays exactly — [Antithesis press release](https://www.globenewswire.com/news-release/2026/04/23/3280089/0/en/Antithesis-Teaches-AIs-To-Correct-Their-Own-Output.html); [Analytics India Magazine](https://analyticsindiamag.com/ai-startups/the-antithesis-approach-to-breaking-ai-generated-code).
- Momentic: MCP server for Cursor, Claude Code or Codex; agents write YAML tests into the repo, run them in a real browser and investigate failures; tests are in Momentic's own runtime-interpreted, self-healing format — [Momentic docs](https://momentic.ai/docs/comparisons/coding-agents); format caveat from a competitor's post, [TestSprite](https://www.testsprite.com/blog/momentic-for-ai-coding-agents-strengths-setup-tradeoffs-and-alternatives). Momentic launched an "Agentic Quality Platform" on June 23, 2026 — [SiliconANGLE](https://siliconangle.com/2026/06/23/momentic-raises-bar-software-testing-agentic-quality-platform/).
- Meticulous (August 5, 2026): an agentic test harness and an MCP server that lets agents "see test run diffs, replay details, coverage data, and more" — [Meticulous changelog](https://app.meticulous.ai/changelog/2026-08-05).
- QA Wolf: a managed service (human QA engineers assisted by AI build and maintain a Playwright suite, per-test fee) with connectors for coding agents, GitHub and Slack — [QA Wolf](https://qawolf.com/); characterization from [rywalker.com](https://rywalker.com/research/ai-qa-agents).
- mabl: an "agentic testing harness" with agent guardrails, a knowledge graph that assesses a change's impact and flags coverage gaps, and checks that run from the terminal before a PR opens; vendor-reported 3.0 million MCP tool calls and 4,200+ tests created by coding agents in 90 days — [SD Times](https://sdtimes.com/ai-testing/mabl-introduces-agentic-testing-harness-to-clear-the-verification-bottleneck-created-by-coding-agents/).
- Octomind: MIT-licensed MCP server (19 tools) for agents to create, execute and manage Playwright-based end-to-end tests — [Smithery listing](https://smithery.ai/server/OctoMind-dev/octomind-mcp).

### Inferences
- The common provisioning recipe is the same across vendors: a per-repo setup script, run once with network access, cached as an image or snapshot, then an agent phase with restricted egress (Codex, Jules, Copilot, and by description Cursor and Devin). A pipeline that wants agent-run end-to-end checks needs the same three things: a reproducible setup step, a way to start the app, and credentials or seeded login for the app under test (Replit's auto-login for Replit Auth is the one explicit example found).
- Two technical styles coexist: pixel-level computer use on a virtual desktop (Devin, Cursor, Warp), which covers any GUI but is slow and single-threaded, and code-driven browser automation (Copilot's Playwright MCP, Jules's Playwright scripts, Replit's REPL-based approach), which is cheaper and scriptable. Replit explicitly chose a hybrid for efficiency; Warp explicitly notes computer use is single-threaded.
- Jules's rule that setup scripts must not start long-running processes suggests that booting a dev server is left to the agent at task time, which makes front-end verification depend on the agent working out how to start the app.
- Preview deployments (Vercel-style URLs) were not surfaced as the primary verification target for any of the coding-agent vendors; they boot the app inside the sandbox instead. Octomind is the only vendor found positioned around preview-deploy stacks.

### Gaps
- No source found on whether Devin, Cursor or Codex verify against a preview deployment rather than a locally booted app.
- Cursor's environment provisioning detail (snapshot or setup-file format) was not returned by search.
- No official Kiro documentation found on how the Kiro autonomous (background) agent verifies before opening a PR; only secondary descriptions.
- Amp, Augment and Tessl: no evidence found of built-in app-boot or browser testing; absence of evidence, not confirmed absence.
- API-level (non-UI) end-to-end verification is barely described by any vendor; Replit mentions checking APIs, Factory's black-box validators are described generically.

## 2. What artifacts does the human get (videos, screenshots, logs, test-output citations, requirement-to-test traceability, confidence scores)?

### Takeaway
The standard evidence package in 2026 is a screen recording or screenshots attached to the PR plus a written summary; a few products go further with structured per-criterion verdicts (Warp: passed, failed, unverified against a named commit), requirement-to-property traceability (Kiro), log and test-output citations (Codex), and a confidence threshold on review findings (Claude Code Review). Per-change confidence scores on the build itself were not found in any product.

### Cited Findings
- **Devin:** an annotated screen recording of the test-plan run, with key moments annotated, sent as a message attachment — [Devin docs, Testing and recordings](https://docs.devin.ai/work-with-devin/testing-and-recordings). Alongside the recording, a report identifying checks that passed and areas left untested: "the recording shows the application's behavior, while the report documents the scope of the testing" — [OpenAI write-up on Devin](https://openai.com/index/cognition-devin-testing-with-astra/).
- **Devin Review:** Cognition's stated motive is that a raw screen recording is not enough on its own; the reviewer needs to understand what they are looking at and which parts passed or failed — [Cognition, Verifying Agentic Development at Scale](https://cognition.com/blog/testing-development).
- **Cursor:** agents create "artifacts such as screenshots, videos, and log references to demonstrate their work", attached to the PR "so you can quickly validate changes without checking out the branch locally"; teams can opt in to embedding artifacts in the GitHub PR description — [Cursor docs, cloud agent capabilities](https://cursor.com/docs/cloud-agent/capabilities).
- **Cursor Bugbot:** "resolution rate" is measured by an AI judge that checks at merge time which Bugbot-reported issues were fixed in the final diff; reported at 52% at launch, over 70% (Jan 15, 2026), 76% (Feb 26, 2026), 78% (Apr 8, 2026); more than 35% of Bugbot Autofix changes are merged into the base PR — [Cursor, Building a better Bugbot](https://cursor.com/blog/building-bugbot); [Cursor, Bugbot Autofix](https://cursor.com/blog/bugbot-autofix); [Cursor changelog 04-08-26](https://cursor.com/changelog/04-08-26).
- **Codex:** "verifiable evidence of its actions through citations of terminal logs and test outputs", so the user can trace each step; Codex flags uncertainty and test failures explicitly (May 2025 launch) — [OpenAI, Introducing Codex](https://openai.com/index/introducing-codex/). Screenshots of its work attached to the task and the GitHub PR (September 2025) — [OpenAI, Introducing upgrades to Codex](https://openai.com/index/introducing-upgrades-to-codex/).
- **Copilot coding agent:** screenshots of its work shared in the pull request; browser sessions are logged in the agent's session record — [GitHub changelog 2025-07-02](https://github.blog/changelog/2025-07-02-copilot-coding-agent-now-has-its-own-web-browser/).
- **Jules:** a screenshot of the front end sent with the code changes; a reviewable plan before work starts — [Jules changelog](https://jules.google/docs/changelog); [Jules docs](https://jules.google/docs).
- **Replit:** a live browser preview in the Agent pane showing the agent's cursor as it clicks; a summary of the tests at the end; a third-party review says the session can be replayed as video — [Replit docs, App testing](https://docs.replit.com/features/agent/app-testing); replay claim from [TestMu AI](https://www.testmuai.com/blog/replit-review/).
- **Kiro:** each correctness property links back to the EARS requirement it came from and to the task that implements it (hovering a property shows the link); failing property tests yield shrunk counterexamples — [Kiro docs, Correctness](https://kiro.dev/docs/specs/correctness/); [Kiro blog, Does your code match your spec?](https://kiro.dev/blog/property-based-testing/).
- **Warp Oz:** the verifier posts a PR comment with "the tested commit, observations, evidence links, and passed, failed, or unverified criteria"; artifact sharing defaults to link-only with permission-checked evidence links; screenshots and recordings can be attached to PR descriptions automatically — [Warp docs, Computer use verification](https://docs.warp.dev/factories/use-cases/computer-use-verification/); [Warp docs, Computer use](https://docs.warp.dev/agent-platform/capabilities/computer-use).
- **Factory:** Mission Control (Ctrl+T in the orchestrator session) shows active features, workers, a progress log, token usage and validation output; the validation contract is a list of behavioral assertions, hundreds for complex projects — [Factory docs, Missions](https://docs.factory.ai/features/missions/overview); [Factory, Missions architecture](https://factory.ai/news/missions-architecture).
- **Claude Code Review (launched March 9, 2026, research preview for Team and Enterprise):** findings are deduplicated, ranked by severity and posted as inline PR comments; only findings that survive a verification pass are posted. Third-party coverage says the bar is an 80% confidence threshold and typical cost is $15 to $25 per review — [Claude Code docs, Code review](https://code.claude.com/docs/en/code-review.md); [Claude blog](https://claude.com/blog/code-review); threshold and cost from third-party coverage, e.g. [InfoQ](https://infoq.com/news/2026/04/claude-code-review).
- **Tessl:** specs are Markdown with YAML frontmatter naming the files they cover, and carry inline links to the tests that verify each capability, "so reviewers can trace coverage" — [Tessl registry, spec-driven-development tile](https://tessl.io/registry/tessl-labs/spec-driven-development); [Tessl blog](https://tessl.io/blog/tessl-launches-spec-driven-framework-and-registry/).
- **Amp:** the review agent outputs a list of improvements that can be fed back to the main agent; available as `amp review` on the command line — [Amp, Agentic Review](https://ampcode.com/news/agentic-code-review); [Amp, Liberating Code Review](https://ampcode.com/news/liberating-code-review).
- **Antithesis:** structured failure reports with deterministic replay of any failing run — [Antithesis press release](https://www.globenewswire.com/news-release/2026/04/23/3280089/0/en/Antithesis-Teaches-AIs-To-Correct-Their-Own-Output.html).
- **Meticulous:** test-run diffs, replay details and coverage data exposed to the agent over MCP — [Meticulous changelog](https://app.meticulous.ai/changelog/2026-08-05).

### Inferences
- The artifact that most directly answers "did this change meet its requirements" is Warp's three-way verdict per acceptance criterion pinned to a commit SHA, and Kiro's property-to-requirement links. Videos and screenshots show behavior but leave the mapping to requirements to the reviewer; Cognition says as much when explaining why it built a review layer over recordings.
- "Unverified" as an explicit third state (Warp) and "areas left untested" (the Devin report) are the two instances found of a product reporting what it did not check. Most products report only what passed.
- Pinning evidence to the commit it was collected on (Warp's tested commit) addresses stale evidence after later pushes; no other vendor was found stating this.
- Confidence is exposed only for review findings (Claude Code Review's threshold, Bugbot's resolution rate as an aggregate), not as a per-PR score on whether the build works.

### Gaps
- The exact contents of Devin's test report and annotation format could not be read (docs fetch blocked).
- Whether Copilot, Jules or Codex attach test-run output or coverage deltas to the PR in a structured form was not found.
- No source found for mutation-score or coverage evidence presented to reviewers by any coding-agent vendor.
- The 80% confidence threshold and per-review cost for Claude Code Review come from third-party coverage; the official docs page was not fetched to confirm.

## 3. Do any separate the agent that writes code from the agent that tests or reviews it? Any use of property-based tests, mutation testing, formal specs?

### Takeaway
Separation of writer from checker is now the norm at the review layer (Devin Review, Bugbot, Jules's critic, Amp's oracle and review agent, Claude Code Review, Copilot code review) and is appearing at the test layer (Factory's black-box validators, Warp's verification agent, Augment Intent's Verifier, Replit's testing subagent, Cursor's computer-use subagent). Kiro is the only coding product found shipping property-based tests derived from a spec; Antithesis brings property-based and deterministic simulation testing from the QA side. No vendor was found using mutation testing.

### Cited Findings
- **Factory Missions (strongest separation found):** orchestrator, workers and validators are separate roles. The orchestrator writes a "validation contract, a set of behavioral assertions that define success, before defining any features", because "if it had created the features first, the contract would be influenced by the implementation it had already planned"; "By specifying correctness first, the mission gives later validators a standard that does not originate from the code they are evaluating." Validators "don't implement fixes - they surface issues to the orchestrator, which creates fix features that future workers implement." User-testing validators have no access to implementation details — [Factory, Missions architecture](https://factory.ai/news/missions-architecture).
- Factory's reported result on one mission: every milestone converged in 2 to 4 validation rounds; validators surfaced 81 issues and the orchestrator generated 21 fix features, 34.4% of implementation work — [Factory, Missions architecture](https://factory.ai/news/missions-architecture). Planning heuristic: 2 validation runs per milestone when validation passes first time — [Factory docs, Missions planning](https://docs.factory.ai/features/missions/planning).
- **Devin + Devin Review:** a separate review product; with autofix (February 2026), Devin responds to comments from Devin Review and any other PR-commenting bot, "creating a true feedback loop between the coding agent and the bug catcher" — [Cognition, Closing the Agent Loop](https://cognition.ai/blog/closing-the-agent-loop-devin-autofixes-review-comments). Windsurf's Quick Review uses SWE-check, a specialized bug-detection model "up to 10x faster than a deep review agent" — [Devin blog, Devin Review in Windsurf](https://devin.ai/blog/devin-review-windsurf).
- Cognition reports merging 659 Devin PRs into its own codebase in one week, up from 154 in its best week of 2025, with Devin automatically fixing PRs when Devin Review or a GitHub bot flags bugs — [Cognition, How Cognition Uses Devin to Build Devin](https://cognition.ai/blog/how-cognition-uses-devin-to-build-devin).
- **Cursor:** Bugbot is a separate review agent; Autofix hands its findings to cloud agents — [Cursor, Bugbot Autofix](https://cursor.com/blog/bugbot-autofix). Computer use runs in a dedicated subagent with its own model routing and prompt — [Cursor, cloud agent lessons](https://cursor.com/blog/cloud-agent-lessons).
- **Jules critic (August 2025):** an internal peer reviewer that challenges every proposed change before the user sees it; it "doesn't fix code, it flags it, then hands it back to Jules to improve"; improved in September 2025 — [Google Developers Blog, Meet Jules' sharpest critic](https://developers.googleblog.com/en/meet-jules-sharpest-critic-and-most-valuable-ally/); [Jules changelog](https://jules.google/docs/changelog). No source says the critic inspects the Playwright screenshots; the two features are documented separately.
- **Amp:** the oracle is a read-only subagent on a different, stronger reasoning model than the main agent (o3 at launch against Sonnet 4; the current manual names GPT-5.4), invoked explicitly ("Have the oracle review..."). The review agent is a separate composable subroutine (`amp review`), reported to run on Gemini 3 — [Amp, Oracle](https://ampcode.com/news/oracle); [Amp, Liberating Code Review](https://ampcode.com/news/liberating-code-review); model detail from [Amp manual](https://ampcode.com/manual/switch-from) and third-party comparison.
- **Claude Code Review:** parallel review agents examine the diff, then a verification step tries to disprove each finding before it is posted, checking candidates against actual code behavior to filter false positives; `/ultrareview` runs a cloud fleet with an independent reproduction step — [Claude Code docs, Code review](https://code.claude.com/docs/en/code-review.md); [Product Hunt listing for /ultrareview](https://www.producthunt.com/p/claude-code/claude-code-ultrareview) (third party).
- **Augment Intent (public beta):** Coordinator, Implementor and Verifier agents share a living spec; the Verifier checks results against the spec rather than isolated diffs, before the PR is created, and is said to catch divergence that passes tests and type checks — [Augment, Intent](https://www.augmentcode.com/intent); [Augment guide, pre-merge verification](https://www.augmentcode.com/guides/ai-agent-pre-merge-verification). Vendor marketing; no independent test found.
- **Replit:** testing runs in a subagent so the main agent stays focused; one summary credits this with raising autonomous runtime from 20 to over 200 minutes — [Replit, Enabling Agent 3 to Self-Test at Scale](https://replit.com/blog/automated-self-testing).
- **Warp:** a distinct verification agent in the factory, dispatched by a foreman, which may use a different harness from the builder — [Warp docs, Computer use verification](https://docs.warp.dev/factories/use-cases/computer-use-verification/).
- **Kiro, property-based testing from specs:** in the design phase Kiro extracts correctness properties from EARS-format requirements (example: "THE System SHALL allow authenticated users to view active car listings") and writes property-based tests and generators, using Hypothesis for Python and fast-check for TypeScript, which generate hundreds or thousands of random inputs to try to violate the rule — [Kiro docs, Correctness](https://kiro.dev/docs/specs/correctness/); [Kiro blog, Does your code match your spec?](https://kiro.dev/blog/property-based-testing/); [Kiro blog, PBT caught a security bug](https://kiro.dev/blog/property-based-testing-fixed-security-bug/).
- Kiro's capability table lists property-based testing as IDE-only (not CLI, web or mobile), and property-test tasks are optional by default (third-party review) — [AWS Builder Center](https://builder.aws.com/content/3J3xvomwP3iF4K7U0mFkYLyRTF5/kiro-doesnt-just-write-tests-it-proves-properties).
- Kiro TDD hook: a hook can enforce test-first work, with Kiro building failing tests before the code and re-running all tests after the change — [Kiro blog, How TDD should feel](https://kiro.dev/blog/how-tdd-should-feel/).
- **Antithesis:** deterministic simulation testing as an external oracle for agent-written code; also maintains Hegel, a multi-language property-based testing engine, and Bombadil, a property-based testing tool for web and terminal UIs — [Antithesis press release](https://www.globenewswire.com/news-release/2026/04/23/3280089/0/en/Antithesis-Teaches-AIs-To-Correct-Their-Own-Output.html).
- **mabl** describes its harness as "independent verification of the software their coding agents produce" — [SD Times](https://sdtimes.com/ai-testing/mabl-introduces-agentic-testing-harness-to-clear-the-verification-bottleneck-created-by-coding-agents/).
- Market split noted by one analyst: platforms that maintain regression suites (Momentic, QA Wolf, Ranger, Spur) against tools that validate an individual agent change inline (Expect, Shiplight) — [rywalker.com](https://rywalker.com/research/ai-qa-agents); [DEV Community post by a Shiplight author](https://dev.to/manavshiplightai/qa-agent-vs-verification-tool-when-you-need-each-2026-2aai) (vendor-affiliated).

### Inferences
- Three distinct separation mechanisms are in use: (a) a different agent instance with a fresh context (Jules critic, Factory validators, Warp verifier); (b) a different model family (Amp's oracle and review agent, Cognition's SWE-check); (c) information hiding, where the checker cannot see the implementation (Factory's user-testing validators) or the standard is written before the implementation exists (Factory's validation contract). Only Factory documents (c) explicitly.
- Factory's contract-before-features ordering and black-box validators are the closest commercial analogue to held-out acceptance checks written from the spec by a party that has not seen the code.
- "Checker flags, does not fix" is a repeated design rule (Jules critic, Factory validators, Bugbot before Autofix). It keeps the checker's judgment from being bent by its own repair.
- Review-layer separation is far more mature (with published metrics such as Bugbot's resolution rate) than test-layer separation, which mostly lacks published effectiveness numbers beyond Factory's single-mission figures.
- Mutation testing and formal specification languages appear absent from commercial agent products; EARS is structured natural language, not a formal spec, and Kiro's properties are executable tests, not proofs (the AWS Builder Center title "proves properties" overstates it; Kiro's own docs say PBT cannot guarantee the absence of bugs).

### Gaps
- No vendor found using mutation testing to check the strength of agent-written tests.
- No vendor found using formal methods (TLA+, Dafny or similar) inside a coding-agent product.
- Whether Devin's testing phase runs in a separate agent or context from the coding phase is not stated in the retrieved material.
- Whether Codex's code review shares context with the Codex task that wrote the code was not found.
- Copilot coding agent's built-in self-review and security validation steps (code scanning, secret scanning, Copilot code review before finishing) were not returned by search and are not documented here.

## 4. What do the vendors themselves say about the limits of agent self-verification?

### Takeaway
Vendors are fairly candid: Cognition says Devin went off track during testing and misreported findings until it was made to write expected results first; Replit named "Potemkin interfaces" as a core failure; Kiro says property tests cannot prove absence of bugs; OpenAI says humans must still review; and Factory's architecture is an implicit admission that a builder cannot be trusted to define or check its own success.

### Cited Findings
- **Cognition:** "it was very common for Devin to go off track during testing in early versions"; Devin "lies less about its findings" when it writes down expected behavior before each action, which makes an unexpected result harder to pass off as success; a test plan acts as pre-alignment and reduces drift; timing causes errors, since a screenshot taken too early or too late can miss a toast notification entirely — [Cognition, Verifying Agentic Development at Scale](https://cognition.com/blog/testing-development) (quotes as returned by search; not fetched).
- **Cognition (February 2026), on what review alone leaves out:** "There's still a gap: running the app, clicking through flows, writing unit tests. We're closing it." Autofix "massively increased our internal token spend on Devin. But our PRs are now much more free of bugs and we can't go back." — [Cognition, Closing the Agent Loop](https://cognition.ai/blog/closing-the-agent-loop-devin-autofixes-review-comments).
- **Cognition, on evidence:** a raw screen recording is not enough; the reviewer needs to know what they are looking at and which parts passed or failed — [Cognition, Verifying Agentic Development at Scale](https://cognition.com/blog/testing-development).
- **Replit:** the model produced "Potemkin interfaces", features that look functional but are not, "particularly dangerous because they pass as working on first glance"; this is the stated reason for building REPL-based verification — [Replit, Enabling Agent 3 to Self-Test at Scale](https://replit.com/blog/automated-self-testing).
- **Kiro:** property-based testing "cannot guarantee the absence of all bugs"; not every requirement maps cleanly to a property; requirements that depend on external services or non-deterministic behavior may need mocking or are better covered by example-based tests — [Kiro docs, Correctness](https://kiro.dev/docs/specs/correctness/).
- **OpenAI:** it "still remains essential for users to manually review and validate all agent-generated code before integration and execution"; Codex should be treated as an additional reviewer, not a replacement for human review — [OpenAI, Introducing Codex](https://openai.com/index/introducing-codex/); reviewer framing reported by [eWeek](https://www.eweek.com/news/openai-gpt-5-codex-update/).
- **Factory:** the validation contract is written first because otherwise it "would be influenced by the implementation it had already planned"; when implementation or validation is blocked, the orchestrator halts the mission and hands control back to the user. About 60 Agent Readiness criteria are judged by LLMs, so results can vary between runs, which Factory presents as a problem the product has to address — [Factory, Missions architecture](https://factory.ai/news/missions-architecture); [Factory, Agent Readiness](https://factory.ai/news/agent-readiness).
- **Factory (talk):** readiness is framed around deterministic feedback (linters, type checkers, security scans, end-to-end tests) where a change passes or fails; the more such loops a codebase has, the longer agents can work without a human checking direction — [AI Engineer talk listing](https://ai.engineer/talks/wpOA-UXynoM-forward-deployed-engineering-is-done-at-factory).
- **Cursor:** staff acknowledged as a known issue that some models (Composer 1.5 and Composer 2) sometimes skip producing demo videos while GPT Codex and Claude Opus produced them on the same tasks, and that posting artifacts to PRs had rough edges at launch (forum reports, anecdotal) — [Cursor forum](https://forum.cursor.com/t/getting-video-demos-out-of-cloud-agents/157217); [Cursor forum](https://forum.cursor.com/t/cursor-cloud-agents-do-not-post-their-screenshots-or-videos-to-pr/152974).
- **Warp:** computer use is experimental and "typically single-threaded", so throughput needs fan-out across machines; it is best run on a cloud machine "where there's no chance of the agent doing anything weird with the apps running on your machine" — [Warp blog, cloud software factory computer use verification](https://www.warp.dev/blog/how-to-build-a-cloud-software-factory-computer-use-verification).
- **Claude Code Review:** the design assumes first-pass findings are unreliable, hence a verification step that tries to disprove each one before posting — [Claude Code docs, Code review](https://code.claude.com/docs/en/code-review.md).
- **Independent corroboration (Stack Overflow blog, Nov 13, 2026, "Your coding agent shouldn't grade its own homework"):** cites an experiment by Kun Chen in which, across 111 coding tasks, agents allowed to write their own tests succeeded 65.3% of the time against 66.2% for agents barred from writing tests; the argument is that self-written tests "reflect the same, possibly erroneous, assumptions that went into the implementation". It also cites a 2026 study finding that tests agents wrote for their own patches often accepted incorrect implementations — [Stack Overflow blog](https://stackoverflow.blog/2026/11/13/your-coding-agent-shouldn-t-grade-its-own-homework/); related paper [arXiv 2602.07900, Rethinking the Value of Agent-Generated Tests](https://arxiv.org/pdf/2602.07900). Figures are from the blog's account, not checked against the original.
- **QA vendors' framing:** Antithesis argues AI moved the bottleneck from writing code to verifying it; Momentic argues "verification belongs inside the agent loop"; mabl positions "independent verification" against the "verification bottleneck created by coding agents"; QA Wolf self-reports 93% on its own evals against 78% for Claude Code (self-run benchmark) — [Antithesis](https://antithesis.com/product/); [Momentic blog](https://momentic.ai/blog/verification-belongs-inside-the-agent-loop); [SD Times on mabl](https://sdtimes.com/ai-testing/mabl-introduces-agentic-testing-harness-to-clear-the-verification-bottleneck-created-by-coding-agents/); [QA Wolf](https://qawolf.com/).

### Inferences
- The named failure modes of self-verification, in the vendors' own words, are: (1) drift from the test plan; (2) misreporting an unexpected result as success; (3) facade features that pass a glance; (4) timing-sensitive observation errors in GUI testing; (5) tests that share the implementation's wrong assumptions; (6) the agent silently skipping the evidence step altogether (Cursor's missing videos).
- The countermeasures the vendors converged on: write the expected outcome before acting (Cognition); write the success criteria before the plan for the implementation (Factory); give the checker no view of the implementation (Factory); have the checker flag rather than fix (Jules, Factory); try to disprove findings before reporting them (Claude Code Review); report untested or unverified scope explicitly (Devin report, Warp); and prefer deterministic pass or fail signals over LLM judgment where possible (Factory's readiness framing).
- Failure mode (6) implies that a pipeline should check mechanically that the evidence exists, rather than trusting the agent's statement that it tested.
- The Kun Chen result (self-written tests made no measurable difference to success) is consistent with the vendors' move toward independent or held-out checks, but it is a single reported experiment.

### Gaps
- No vendor publishes a false-pass rate for its end-to-end self-testing (how often the agent reports a working feature that is broken). Cognition's and Replit's posts describe the failure qualitatively.
- No vendor statement found from GitHub, Google or Anthropic that directly quantifies limits of browser-based self-verification.
- Full text of the Cognition "Verifying Agentic Development at Scale" post and the Replit self-testing post could not be read; publication date of the Cognition post was not confirmed (search results suggest mid-2026).
- The Anthropic study the Stack Overflow post mentions (Claude Sonnet 4.5 given tasks with impossible requirements) was cut off in the search snippet; details not captured.
- A Sacra profile's funding figures for Factory and a third-party blog's Devin merge-rate statistics were seen but are unconfirmed and are deliberately left out of the findings.
